# معماری شبکه — Peer-to-Peer در برابر Client-Server

قبل از اینکه بریم سراغ توپولوژی فیزیکی یا پروتکل‌ها، باید یک تصمیم منطقی رو فهمید: هر device توی شبکه چه نقشی داره — همه با هم برابرن (p2p) یا یه سری device نقش سرویس‌دهنده متمرکز رو بازی می‌کنن (client-server)؟ این تصمیم مستقیماً روی security model، مدیریت account، و scalability شبکه اثر می‌ذاره. خیلی از سوالای امتحان و مصاحبه دقیقاً از همین‌جا میان چون ظاهراً ساده به نظر می‌رسه ولی جزئیاتش قاطی می‌شه.

## معماری Client-Server

توی این مدل یک یا چند device به‌عنوان **server** نقش متمرکز دارن: authentication رو مدیریت می‌کنن، resource (فایل، پرینتر، دیتابیس) رو centralized نگه می‌دارن، و policy رو از یک نقطه push می‌کنن. باقی device‌ها **client** هستن و صرفاً request می‌فرستن.

مثال واقعی: یک شرکت با ۵۰ کارمند. یک **Domain Controller** (مثلاً Windows Server با Active Directory) داره. کارمندا با یک username/password مرکزی لاگین می‌کنن، فایل‌ها روی یک **file server** مشترکه، و پرینترها هم از طریق **print server** مدیریت می‌شن.

مزیت‌ها:
- Authentication متمرکز — یک بار account رو می‌سازی، همه‌جا کار می‌کنه (SSO تقریبی).
- Policy مرکزی — مثلاً GPO توی AD می‌تونه همزمان روی ۵۰۰ کاربر اعمال بشه.
- Backup و audit راحت‌تره چون داده یک‌جا جمعه.
- Scale می‌کنه — از ۱۰ کاربر تا ۱۰٬۰۰۰ کاربر مشکلی نداره.

معایب:
- Single point of failure — اگه سرور بخوابه (مخصوصاً DC)، کل شبکه از کار می‌افته.
- هزینه‌ی سخت‌افزار و لایسنس سرور بالاست.
- نیاز به آدمین متخصص برای نگه‌داری داره.

## معماری Peer-to-Peer (P2P)

اینجا هیچ device نقش متمرکز نداره. هر ماشین هم client هست هم server — یعنی هم می‌تونه resource خودش رو share کنه، هم به resource بقیه دسترسی داشته باشه. هیچ authentication مرکزی وجود نداره؛ هر device خودش account‌های خودش رو مدیریت می‌کنه.

مثال واقعی: یک خونه یا دفتر خیلی کوچیک با ۴-۵ سیستم روی Windows. کاربر A روی سیستم خودش یک فولدر رو share می‌کنه، کاربر B مستقیم از طریق `\\PC-A\Shared` بهش وصل می‌شه. هیچ سرور واسطه‌ای نیست.

مزیت‌ها:
- ارزون — نیازی به سرور اختصاصی و لایسنس سرور نیست.
- راه‌اندازی سریع — برای شبکه‌های خیلی کوچیک همون روز جواب می‌ده.
- بدون single point of failure متمرکز — اگه یه ماشین بخوابه فقط resource خودش قطع می‌شه.

معایب:
- **Scale نمی‌کنه.** بالای ۱۰-۱۵ device مدیریت account و permission به‌صورت دستی عملاً جهنم می‌شه.
- Security ضعیف‌تره — هیچ audit trail مرکزی، هیچ enforcement مرکزی policy وجود نداره.
- Backup پراکنده‌ست — هر داده روی یک ماشین جدا نگه داشته می‌شه.

> **تله‌ی رایج امتحان:** خیلی‌ها فکر می‌کنن p2p یعنی «بدون سرور به‌طور کلی» ولی نه — منظور اینه که **هیچ device نقش اختصاصی و متمرکز سرور رو نداره**، نه اینکه یک device نمی‌تونه چیزی رو share کنه. هر device هم‌زمان می‌تونه server (share-کننده) و client (مصرف‌کننده) باشه؛ فرقش با client-server اینه که این نقش متقارنه و متمرکز نیست.

### جدول مقایسه‌ی P2P در برابر Client-Server

| ویژگی | Client-Server | Peer-to-Peer |
|---|---|---|
| Authentication | متمرکز (مثلاً AD / LDAP) | محلی، روی هر device جدا |
| Scalability | بالا (تا هزاران کاربر) | پایین (معمولاً تا ~۱۰ device) |
| هزینه اولیه | بالا (سرور + لایسنس) | پایین |
| Single point of failure | بله (سرور مرکزی) | نه به‌صورت متمرکز |
| Policy enforcement | مرکزی و خودکار (GPO) | دستی، روی هر device |
| مثال دنیای واقعی | شرکت با Domain Controller | خونه یا دفتر ۴-۵ نفره، یا torrent |
| مدیریت permission | یک‌بار روی سرور تعریف می‌شه | باید روی تک‌تک ماشین‌ها تعریف بشه |

## Workgroup

Workgroup اسم فنی‌ای‌ه که مایکروسافت برای پیاده‌سازی p2p روی Windows به کار می‌بره. وقتی چند سیستم Windows رو توی یک workgroup می‌ذاری (مثلاً همه‌شون اسم workgroup‌شون `WORKGROUP` یا یک اسم دلخواهه)، فقط یعنی از نظر **name resolution** (از طریق NetBIOS یا mDNS/LLMNR توی نسخه‌های جدید) همدیگه رو راحت‌تر پیدا می‌کنن — نه اینکه authentication یا policy مشترکی داشته باشن.

نکته‌ی مهم: **هر سیستم توی workgroup، database امنیتی خودش رو داره** (SAM — Security Accounts Manager). یعنی اگه کاربر `ali` روی PC-A هست و می‌خواد به شیر روی PC-B دسترسی داشته باشه، باید یک اکانت `ali` با همون پسورد **دوباره روی PC-B** هم ساخته بشه؛ وگرنه با پاپ‌آپ پسورد گیر می‌کنه یا با guest access محدود می‌مونه.

```powershell
# ساخت اکانت محلی روی PC-B که باید دقیقاً مطابق اکانت PC-A باشه
net user ali P@ssw0rd123 /add
net localgroup "Users" ali /add
```

این دقیقاً همون نقطه‌ایه که وقتی تعداد سیستم‌ها زیاد بشه، مدیریت workgroup غیرقابل‌تحمل می‌شه — چون هر پسورد عوض بشه، باید روی همه‌ی سیستم‌ها دستی sync بشه.

### Workgroup در برابر Domain

| ویژگی | Workgroup | Domain |
|---|---|---|
| مدل امنیتی | SAM محلی روی هر ماشین | Active Directory متمرکز |
| حداکثر اندازه‌ی عملی | ~۱۰-۲۰ سیستم | هزاران سیستم |
| نیاز به سرور | خیر | بله (Domain Controller) |
| مدیریت پسورد | دستی روی هر سیستم | متمرکز، یک‌بار |
| Group Policy | ندارد | دارد (GPO) |

> **تله‌ی امتحان:** سوال می‌پرسن «چرا کاربر نمی‌تونه به شیر روی سیستم دیگه توی workgroup وصل بشه؟» جواب رایج غلط اینه که «فایروال بلاکش کرده». جواب درست معمولاً اینه که **credential روی مقصد وجود نداره یا مطابقت نداره**، چون هیچ authentication مرکزی‌ای رد و بدل نمی‌شه.

## سیاست‌ها در P2P (Security Policy)

توی client-server، policy (مثل «حداقل طول پسورد ۸ کاراکتر» یا «قفل شدن بعد از ۵ بار پسورد غلط») از طریق GPO یک‌جا تعریف و به همه push می‌شه. توی p2p هیچ مکانیزم مشابهی وجود نداره — **policy، اگه بخوای، باید دستی و جداگانه روی هر device تنظیم بشه** (مثلاً از طریق Local Security Policy در Windows: `secpol.msc`).

این یعنی:
- هیچ enforcement مرکزی‌ای وجود نداره؛ اگه یه نفر روی سیستم خودش policy رو سست کنه، هیچی جلوش رو نمی‌گیره.
- Audit و compliance تقریباً غیرممکنه چون log‌ها هم پخش و محلی‌ان.
- امنیت کلی شبکه به اندازه‌ی **ضعیف‌ترین سیستم** توی workgroup‌ه — یک سیستم با پسورد ضعیف کل شبکه رو در معرض خطر می‌ذاره.

به همین دلیل توی محیط‌های واقعی، p2p/workgroup فقط برای شبکه‌های خیلی کوچیک (خونگی، آزمایشگاه، دفتر زیر ۱۰ نفر) توصیه می‌شه؛ به محض این‌که نیاز به مدیریت متمرکز پسورد، audit، یا compliance پیدا بشه، باید به سمت domain حرکت کرد.

## Access Control List (ACL)

ACL لیستیه که مشخص می‌کنه **کی** به یک resource (فایل، فولدر، پورت روی روتر، و...) **چه سطحی** از دسترسی داره. مفهوم ACL مستقل از p2p یا client-server‌ه، ولی نحوه‌ی مدیریتش فرق می‌کنه:
- توی client-server: ACL معمولاً بر اساس **گروه‌های دامنه** تعریف می‌شه (مثلاً `Domain\Accounting-Team: Read/Write`)، پس مدیریتش متمرکزه.
- توی p2p: ACL باید بر اساس **اکانت محلی هر سیستم** تعریف بشه، پس باید تک‌تک روی هر device تنظیم بشه.

### ACL در سطح فایل‌سیستم (Windows)

```powershell
# نمایش ACL فعلی روی یک فولدر
icacls "C:\Shared"

# اضافه کردن دسترسی Full Control برای یک کاربر
icacls "C:\Shared" /grant "ali:(OI)(CI)F"

# حذف دسترسی یک کاربر
icacls "C:\Shared" /remove "ali"
```
پرچم‌های `(OI)` و `(CI)` یعنی این permission به object‌های داخلی (Object Inherit) و container‌های داخلی (Container Inherit) هم ارث می‌رسه — یعنی روی زیرفولدر و فایل‌های داخلش هم اعمال می‌شه.

### ACL در سطح فایل‌سیستم (Linux)

```bash
# نمایش ACL روی یک دایرکتوری
getfacl /shared

# دادن دسترسی rwx به یک کاربر خاص (جدا از owner/group معمولی)
setfacl -m u:ali:rwx /shared

# دادن دسترسی read-only به یک گروه خاص
setfacl -m g:accounting:r-x /shared
```
این دقیقاً همون چیزیه که permission ساده‌ی `chmod` (owner/group/other) نمی‌تونه بده — ACL یعنی می‌تونی به **چند کاربر یا گروه دلخواه**، جدا از owner اصلی، سطح دسترسی متفاوت بدی.

### دو نوع ACL که قاطی می‌شن

| نوع | کاربرد | مثال |
|---|---|---|
| **DACL** (Discretionary ACL) | مشخص می‌کنه کی مجاز به دسترسیه و چه سطحی | `icacls`, `chmod`/`setfacl` |
| **SACL** (System ACL) | مشخص می‌کنه کدوم access attempt‌ها باید **log** بشن (audit) | Auditing policy توی Windows |

> **تله‌ی رایج:** وقتی می‌گن «ACL»، اکثر جاها منظورشون DACL هست (کنترل دسترسی)، نه SACL (audit). توی سوال‌های امتحان دقت کن کدوم رو می‌پرسه — اگه صحبت از «چه کسی می‌تونه بخونه/بنویسه» باشه یعنی DACL، اگه صحبت از «چه چیزی log بشه» باشه یعنی SACL.

### سناریوی عددی

فرض کن یک فولدر share شده داری که ۵ نفر بهش نیاز دارن، ولی با سطح دسترسی متفاوت:
- ۲ نفر (تیم مالی) باید Read/Write داشته باشن.
- ۲ نفر (تیم بازاریابی) فقط Read داشته باشن.
- ۱ نفر (مدیر) Full Control (شامل تغییر permission) داشته باشه.

توی client-server، این یعنی ۳ گروه دامنه (`FinanceRW`, `MarketingRO`, `Admins`) می‌سازی، ۵ کاربر رو توش می‌ذاری، و ACL رو فقط یک‌بار روی همون ۳ گروه تعریف می‌کنی — عوض شدن اعضا تاثیری روی ACL خود فولدر نداره.

توی p2p، چون گروه دامنه نداری، یا باید همون ۵ اکانت رو دستی روی سیستمی که فولدر رو share کرده بسازی و جدا-جدا permission بدی، یا از local group استفاده کنی — که مدیریتش با اضافه/کم شدن هر کاربر جدید، دستی و خطاپذیره.

## مرور سریع

- **P2P**: هیچ نقش متمرکز سرور نیست، هر device هم client هم server، هر ماشین SAM/account خودش رو داره.
- **Client-Server**: نقش متمرکز سرور (auth، policy، resource)، scale بالا، اما single point of failure.
- **Workgroup** = پیاده‌سازی p2p روی Windows؛ فقط برای name resolution کمک می‌کنه، auth مشترک نمی‌سازه.
- روی workgroup، برای دسترسی به شیر روی سیستم دیگه باید **همون اکانت با همون پسورد** روی مقصد هم وجود داشته باشه.
- **Policy روی p2p متمرکز نیست** — باید دستی، جدا-جدا تنظیم بشه؛ امنیت کل شبکه به اندازه‌ی ضعیف‌ترین سیستمه.
- **ACL** = کنترل دسترسی روی resource؛ روی client-server بر اساس گروه دامنه (متمرکز)، روی p2p بر اساس اکانت محلی (پخش‌شده).
- **DACL** = کنترل دسترسی، **SACL** = audit/logging — این دو رو با هم قاطی نکن.
- Threshold عملی برای گذر از p2p به domain: معمولاً حدود ۱۰-۲۰ device.
